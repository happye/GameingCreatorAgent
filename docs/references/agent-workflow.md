# 多工具开发与交接协议

适用工具：Codex、Claude Code、Grok Build，以及以后接入的开发 Agent。工具可以按可用额度切换；项目范围、技术决策和验收标准由仓库文件保持一致。大型项目按阶段推进，当前仍先完成 Phase 0。

## 共享记录及职责

| 记录 | 用途 | 并行开发时的写入者 |
| --- | --- | --- |
| `AGENTS.md`、`docs/` | 共享规则、规格和架构决策 | 负责对应文档的任务 owner；公共规则由集成负责人更新 |
| `feature_list.json` | 特性 ID、优先级和验收结果 | 集成负责人在验证后更新 |
| `docs/exec-plans/assignments.md` | 活跃任务、分支、文件归属与交接状态 | 协调本轮工作的工具会话或用户指定的负责人 |
| `docs/exec-plans/sprint-Fxxx.md` | 单项任务的计划、过程、验证与交接 | 该任务 owner |
| `HANDOFF.md` | 当前顺序开发或集成会话的恢复入口 | 当前顺序开发者或集成负责人 |
| `progress.md` | 已交付工作的历史记录 | 当前顺序开发者或集成负责人 |
| `docs/exec-plans/human-inputs.md` | 需要用户标注、确认、手动操作或授权的事项与完成证据 | 集成负责人汇总；worker及时提供触发与影响 |

这些文件是协作约定，不是自动锁或调度系统。并行启动前先协调分工；仅在各自分支修改分工表无法向其他会话发布任务占用。

## 子Agent按能力选模型（持久规则）

关键交付采用[Planner→Generator→Evaluator](development-agent-pipeline.md)的合同与独立评估；本项目Codex三角色配置已补齐，未将配置生成称为已执行。简单工作由主控直接做并明确单Agent；只读规划／评估返回内容由主控保存，不追加重复reviewer。换工具先核对原生能力与可用型号，不假称Codex配置对所有工具有效。

用户于2026-10-11明确要求按任务能力选择模型以节省token／额度。需要委派的独立任务遵循[Codex分工指南](codex-agent-routing-guide.md)：查代码Luna/high、看进度Luna/low、开发和一般审查Sol/medium、关键边界审查Sol/high、复杂设计Astra/low，默认Luna/medium。简单任务直接做，不重复审查、不让进度Agent高频重复播报；不对全部子Agent复制主模型／整段历史。当前工具无法识别新角色时，用可用default／worker加明确model／reasoning_effort与最小上下文，本工具用fork_turns=none；新会话原生加载角色配置，旧角色不热切换。

只用当前运行时确实支持的模型，并用执行记录核对；不按Agent自称或别的产品的模型别名判断生效。写任务仍必须分配owner、保护他人改动；只读角色不得变更项目或执行费用／上传。低模型不足时给证据明确升级一次，不反复试错后再无限重查；主模型保持用户设置。个人与项目配置可按指南安装，权限继承限制和实际验证边界如实汇报，不能承诺未经测量的节省比例。其他工具保持此偏好，但按自己的受支持模型实现：Claude Code见[Claude分工指南](claude-agent-routing-guide.md)。

## 开始一个会话

跨对话先读HANDOFF顶部与接手清单，直接执行已授权本地任务，不从历史暂停／未授权／待标注重启。停止汇报说明直接触发、整任务中断链路、严重度、已保存进度／费用和续作顺序；区分质量保护与流程缺陷，P1阻断优先修复。长钟馗当前入口docs/exec-plans/resume-long-zhongkui-20261011.md。

1. 在正确的仓库或分配的 worktree 中启动工具，检查 `git status --short`、当前分支和最近提交。
2. 读取 `AGENTS.md`、`HANDOFF.md`、`feature_list.json`；已有分工时读取自己的 sprint 文件。按任务读取相关规格、架构和规范。
3. 运行 `./scripts/init.ps1 -CheckOnly`。开始构建前重新运行完整环境检查；旧交接里的环境结果不替代当前检查。
4. 接续已分配任务。新任务先在分工表记录 owner、分支和文件归属；不要直接抢做其他工具正在处理的特性。

## 主线交付优先（持久规则）

用户于2026-10-06纠正开发方式：按照总方案和已设计的开发路径推进大方向，小bug先记录，能快速修就修，不能快速修的留待后续，禁止在同一个问题上反复耗费时间和tokens。所有Agent恢复时须与汇报偏好一起加载。

每轮选择计划中的一个主要交付并说明其所在阶段、依赖和验收结果；围绕该交付完成可用功能。非阻断小问题只做有证据的直接修复，需要多轮调查或试错就写入tech-debt.md，保留影响与复现后返回主线。会阻断本轮主要交付或危及数据、费用等关键边界的问题才升为优先事项，原因须明确。不要将连续微修／诊断页面增强／文档堆积或无变化的完整回归当作主要成果。原阶段门槛、授权和费用约束继续有效，不为了展示进度虚报通过或隐式付费。

## 持久化工作与汇报模式

用户于2026-10-06明确要求：每次关键改动都要给出不那么技术味的详细汇报，并说明接下来要做什么。这是本项目所有 Agent 的持续工作规则，覆盖 Codex、Claude Code、Grok Build、子 Agent、工具切换及会话恢复。共享规则保存在 `AGENTS.md`，各工具入口引用本协议；任务进度保存在 sprint 和 `HANDOFF.md`。

关键改动指可用能力、操作流程、模型对画面的理解、费用处理发生变化，或发现影响验收的重要问题。每个这样的节点完成后主动汇报，不能只在用户追问或结束会话时说明。普通命令、排版修正和内部小步骤无需逐条长报；持续工作时仍保持简短进度更新。

一次汇报用连贯的中文讲清四件事：

1. **现在能做什么**：先说结果，结合用户的视频或查询例子解释具体变化。
2. **使用上有什么帮助**：说明省掉哪些操作、提高哪些判断能力，或避免什么已发生的问题。
3. **验证到了什么程度**：区分程序检查、实际页面检查、真实模型结果和用户人工核对；说明仍不准确或尚未验证的部分，不能把测试通过称为内容理解准确。
4. **接下来做什么**：说明下一项具体工作及它要解决的问题；已有授权内继续推进，不把汇报变成重复确认。

不要用文件名、提交号、专业术语或测试数量堆成主体；确有帮助的技术证据放在使用效果之后。不要为显得完成而隐藏失败、费用预留或未通过的验收。子 Agent 向集成负责人按同样格式提交结果，由负责人在关键节点汇总给用户，避免重复播报。

汇报后将用户偏好、已说明的关键结论和下一步保留在共享记忆及当前交接记录中。接手者先加载规则，再以工作树和证据检查进度；不得把此模式当作一次聊天中的临时要求。

## 顺序接力：额度不足或切换工具

### 人工协助与里程碑同步（持久规则）

关键节点同步时必须同时更新[进度看板](../exec-plans/progress-board.md)：功能完成数、F006步骤、人工待办数、技术债计数、正在做／下一步及“最后更新”行（规则见`AGENTS.md`“Persistent progress board”）。

用户于2026-10-11正在填写原片表时要求逐框通俗解释。交付人工表单时先说明用途、每个字段填什么／为什么、一个明确标为假设的完整示例，以及登记与下载保存的区别；解释哪些项管整份记录、哪些项管单条片段、哪些可留空。真人已在填写时不覆盖页面包或假定已保存；说明后再询问最新记录路径、完成范围与真实缺例，避免把界面术语当成操作指导。原片表的具体口径见[字段说明](benchmark-reference-fields-guide.md)。

用户于2026-10-07要求第一时间提醒并记录任何需要人工帮助的事务。发现需要标注、素材分组、手动提交、业务判断或新费用授权时，立即说明要做什么、在哪里操作、何时需要、影响哪项交付；同步 `docs/exec-plans/human-inputs.md` 的状态与证据。不要替人判分，不把沉默或持续开发当授权。已提醒的同一待办只在触发实际操作、状态变化或需要用户决策时再次提醒；不每轮重复催促。人工待办不阻止没有该依赖的开发。

每个关键实现、验证、交付、发布或阶段变化节点，集成负责人同步当前 sprint、`HANDOFF.md`、分工表和 `progress.md` 的当前摘要；核对阶段门槛与特性验收状态。顶部让用户能直接看到最后交付、开发中、人工待办和下一动作，旧报告与失败作为历史保留。不得等会话结束才更新，也不得用文档数量替代开发。子 Agent 在节点完成时向负责人提供变化，公共记录由负责人串行汇总。

进度要持续落盘，不等用户提醒或会话结束：每个实现/验证节点、依赖变更、实测失败及长任务启动前，更新对应 sprint；关键状态同时更新 `HANDOFF.md`。协调者保留可恢复的 Git 检查点，未验收代码可提交但必须维持 `passes: false`，注明最后通过的检查与尚未运行的检查。模型额度无法可靠预知，禁止把交接推迟到额度耗尽时。远端失败时记录本地提交和补推命令，不把未推送称为远端已同步。

停止前把当前行为、未完成部分、最后一次验证、未提交文件和下一条具体操作写入 sprint 文件，并更新 `HANDOFF.md`。保留失败信息和阻塞原因；未验收功能继续 `passes: false`。如果会话突然中断，接手者以工作树和测试结果为准，补齐缺失记录，不把聊天中的“完成”当作验收证据。

同一台机器可以从原分支直接接续，先检查未提交变更归属。云端会话（例如链接到本机的Claude云容器）按换机器处理：在独立克隆开发并经GitHub同步，记录哪些检查在Linux执行、哪些Windows专属检查（verify.ps1、项目内FFmpeg、真实素材）仍待本机完成；本机工作树有其他工具活跃写者时不写入，不上传素材或项目数据库。换机器时先保存可恢复的提交或明确的补丁，把工作分支同步到已有远端；未提交变更和本地视频不会随 Git 自动传输。保存未完成检查点时记录未通过的检查，保留特性未验收状态。

接手者在分工表及 sprint 中记录新的 owner 和工具，核对环境与必要验证后继续。不要重复初始化仓库或重新实现已完成模块。

## 并行开发

独立 worktree 必须区分只读测试和环境准备。只读借用主树固定 Python 时，可加载主树 `scripts/env.ps1` 后设置工作树 `PYTHONPATH`，Python 始终 `-B`；不得在此环境调用 uv sync/venv 等写操作。准备依赖或运行时时，必须加载目标 worktree 自己的 `scripts/env.ps1`，明确断言 `UV_PROJECT_ENVIRONMENT` 指向它自己的 `.venv`、`UV_PYTHON_INSTALL_DIR` 指向它自己的 `.tools/python`，再执行写操作；`uv --project` 不覆盖前者。可明确复用已验证下载缓存，但不能共用可变虚拟环境。2026-10-29已实证遗漏会分别改写共享标准库字节码、误删主树依赖，详见 `.learnings/ERRORS.md`；修复均限项目内，不改全局配置。

只在确有同时写入需求时使用独立分支/worktree；主控及串行依赖任务复用当前树，只读任务不创建副本。并行写者仍不得同时修改同一目录；先明确模块依赖和文件归属，最多三个活跃写者树，放在`.worktrees/`，不得放入`.cache/`。优先复用空闲工作槽，不为每个小步骤再复制一棵树。示例：

```powershell
git worktree add .worktrees/worker-slot-1 -b codex/F002-media
```

协调者把任务、分支、范围和依赖提供给每个会话。公共接口先由一个 owner 落地并集成，其他任务再基于它开发。修改跨任务接口时记录变更并协调所有受影响 owner，不覆盖其他会话的修改。

并行 worker 把证据和恢复信息写入自己的 sprint 文件；公共特性结果、根交接和历史日志由集成负责人串行汇总。合并后检查冲突、文档和相关测试，再更新 `passes`。禁止仅凭某个工具的口头总结直接标记通过。

工作树有生命周期：已集成且需要保留的源内容有Git提交或最小补丁依据后，检查没有活跃写者/未保存文件，再用`git worktree remove`释放已完成工作树；不得把长期留下整树作为默认备份。未完成工作只保留必要恢复检查点，不拷贝运行时/模型/媒体到另一整树。失败信息需要保留，失败的无限补帧/补音频中间文件不属于必须长期保存的信息。

测试的tmp_path媒体在fixture结束后自动回收，保留小型报告/失败元数据。媒体进程同时执行单文件、私有目录和磁盘余量预算，不能仅靠超时；容量超限不能当作成功。详见[缓存维护](cache-maintenance-guide.md)。

## 结束与验收

记录验证命令、结果、必要输出位置及未验证项。一个工具实现后可由另一个工具评审，但评审必须使用仓库中的标准与证据。小任务完成相关检查即可；大型变更保留执行计划和决策依据。不要因为换工具修改范围、重选技术栈或降低 70% 的 Phase 0 检索门槛。
