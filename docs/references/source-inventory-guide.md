# 素材来源盘点：找出画面相同的录像

登记验收分组前，先用这个本机命令检查素材是否有“字节不同、画面相同”的情况，例如宣传片剪入了实机镜头。它给出具体证据，帮你决定哪些录像应归同一原录制会话；它不分析、不调用付费模型、不写入素材目录，也不会替你分组。

## 使用

在仓库根目录：

```powershell
./scripts/inventory-sources.ps1 -InputPath GameVideos -OutputPath artifacts/source-inventory.json
```

`-InputPath`可给多个文件或目录；目录会递归查找`.mp4`、`.mkv`、`.webm`（OBS的MKV录像也在内，2026-10-25起）并固定排序，其他扩展名的文件需逐个写明路径。输出文件必须放在素材所在目录之外，先写临时文件再原子替换。也可直接运行`python -m gamingcreator inventory-sources --input <路径...> --output <json>`。

## 报告内容（`source-inventory-v2`）

- 每个来源：路径、字节数、SHA256、来自流时钟的时长（微秒）、视频编码／尺寸／帧率、采样帧数和有信息量的帧数，以及`crop`（见下，无黑边时为null）。
- `duplicateGroups`：SHA256完全相同的副本。
- `sharedFootageCandidates`：两个不同文件之间疑似共用画面的证据：偏移秒（A时间减B时间）、相近票数／可比票数（`matchedVotes`／`comparedVotes`，相邻±1偏移上的相关投票，不是帧数）、A方不同相近采样数（`matchedFramesA`）、该对的背景相近率、校正后概率、`clusterCount`，以及最密集连续一段（相近采样间隔不超过4个采样，即2秒）的A／B首末时间，远处的偶然命中不会拉长范围。时间是2帧／秒采样序号换算的近似秒，不是逐帧精度。`mirrored`为true表示B左右翻转后才与A匹配（镜像）。
- `notComparable`：有效画面不足20个采样的来源（如全黑画面只有声音），不参与比较，不能据此判断是否独立。
- `failedSources`：探测或解码失败的文件（编号、路径、错误码、说明），其余素材照常比较；只要报告写出，命令就返回0，请看控制台清单。
- `parameters`（含黑边检测与镜像开关）、`ffmpegVersion`、`limitations`；`humanDecisionRequired`恒为true，不含任何`recordingGroup`建议。

## 怎么判断

每个文件按2帧／秒缩成9x8灰度图并生成64位差值哈希；低对比度帧（如纯黑、纯色）不参与。同一偏移上汉明距离不超过10的帧算相近，相邻±1采样偏移合并投票，再对比该对文件整体的偶然相近率，做二项检验并按偏移数校正（Bonferroni），校正后概率不超过1e-6且至少20个可比采样才报告。票数彼此相关，概率只是名义排序分数，不是精确概率。采样方式、哈希、阈值均取自实际使用的提取器与参数。例如“PV与实机”在某个固定偏移上约四分之一的帧相近，而其他偏移不到7%，就会被列出。

## 黑边与镜像

- 黑边：每个来源先用项目内ffmpeg的`cropdetect`（`fps=1,cropdetect=limit=24:round=2:reset=0`，扫描整段视频，取所有被检测框的并集）得到内容框。仅当框在画面内、至少去掉宽或高的2%（`minCropRemovedFraction`，忽略轻微暗角）、且保留不少于原画面40%面积（`minCropAreaFraction`）时才采用；采用后签名滤镜变为`crop=W:H:X:Y,fps=2,scale=9:8:flags=area,format=gray`，框写入该来源的`crop`（`width/height/x/y`，原像素）。没有黑边的来源`crop`为null，签名与v1完全相同。这一步多一次整段解码（1帧／秒），盘点耗时随之增加。
- 镜像：同一次解码里，对每个9x8灰度缓冲再计算逐行反转后的哈希，不需要二次解码。每对来源分别做“A对B正常”和“A对B镜像”两次检测，各自按偶然相近率做校正，再按显著性合并；覆盖同一段画面的较弱结果被去重。候选的`mirrored`标出是否经镜像匹配；控制台摘要会标“镜像”。
- 报告`parameters`里的`cropDetectFilter`、`cropFilter`、`minCropAreaFraction`、`minCropRemovedFraction`、`mirror`取自实际使用的提取器。检测按解码后画面坐标，旋转元数据使宽高与ffprobe不一致时，超出画面的框会被忽略（当作不裁）。

## 限制

- 命中只说明有共用画面的证据，仍需人工看视频确认；未命中不证明独立。
- 静态标题／logo卡（黑底白字、白底logo等）会被排除：相近帧里至少要有3个互不相似（汉明距离不小于6）的画面，且A、B两侧都要满足；因此动作很少的极短共用镜头可能漏检。同一对文件里与更显著结果覆盖同一段画面的候选只保留一个。
- 非均匀黑边的裁切（如画面内容被裁掉一部分）、大面积叠字、变速和很短的低动作镜头仍可能漏检；画面长期近乎相同的素材（固定界面、重复标题）区分度低，可能不报告。
- 黑边检测取全片1帧／秒检测框的并集：片头闪白、角标或只有部分片段带黑边时通常不裁边，这时只会漏检，不会误判共用；带旋转元数据的视频可能被当作不裁边。
- 正向与镜像各自做一次检验、各自按偏移数校正（每对来源整体有效阈值约为2×1e-6）；左右对称的画面可能把原样匹配标成`mirrored=true`，这只是标签，冻结阻断不依赖它。
- 报告不改变冻结计划，也不自动分配录制组；是否同组由人工在登记时决定。

## 用于冻结（`benchmark-freeze-v2`）

冻结时可把本报告交给[验收准备](./benchmark-preparation-guide.md)（`-InventoryPath`／`--inventory`，工作台冻结步骤也可上传）；也可让冻结自己盘点（`-AutoInventory`／`--auto-inventory`，工作台默认勾选），用同一套代码对计划中的全部录像生成同样的报告字节并存进冻结包，无需先单独运行本命令，与上传互斥。冻结包原样保存报告为`source-inventory.json`，严格接受`source-inventory-v1`（今天之前生成的报告继续有效，原字段集与原限制文案）和`source-inventory-v2`（来源多`crop`、候选多`mirrored`，新限制文案）。两者都校验字段集、`humanDecisionRequired`为true、`limitations`与对应版本的生成端文案完全一致、SHA256格式、来源编号唯一、候选引用已知来源，v2另校验`crop`为null或画面内的框、`mirrored`为布尔值；最大4MiB。限制文案若再修改，需要升级为新的报告版本。冻结派生记录里，v2的共用画面对带`mirrored`，v1报告派生内容与此前字节一致。冻结录像按SHA256匹配盘点来源（同SHA不同时长拒绝）；匹配不到时，仅当盘点失败项的路径（不区分大小写）相同才记为“读取失败”，否则记为“报告中没有”。

共用画面证据映射到冻结录像后，若两段登记在不同录制组、或跨开发／测试，冻结准备会列出阻断；有录像缺失、失败或有效画面不足也会阻断。未发现证据只显示“无证据”，不是“独立”；分组始终由人决定。旧v1冻结不核对盘点。

上传到工作台前请原样使用命令生成的报告文件：用其他程序（例如PowerShell 5.1）重新保存会加BOM或改变换行，字节和SHA256随之改变；冻结包保存的是上传字节，SHA256以此为准。
