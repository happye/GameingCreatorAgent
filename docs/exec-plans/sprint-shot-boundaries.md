# 本地镜头切分与黑屏检测（shot-boundaries-v1，2026-10-26第四会话）

所属阶段：Phase 0。依据：产品规格“质量不过关先改进理解／检索”，总方案§15–16本地负责scene detection与黑屏检测（看板A组“场景切分”），技术债TD007“多帧输入可能跨镜头关联”。主要交付：一个只读、不花钱的本地命令，找出原片里的镜头切换和黑屏段，并标出已保存的哪些事件、哪些多帧分析窗口把不同镜头的画面混在了一起。真实验收仍等用户分组决定，本项不依赖它。单Agent主控实现，独立评估见第五节。

## 一、对用户来说多了什么

- **一条命令看清“模型看到的几张图是不是同一个镜头”。** `./scripts/detect-shots.ps1 -Project <项目> -Run <任务> -OutputPath <新报告.json>`：本机用项目自带FFmpeg扫一遍原片，给出每个镜头切换时间、黑屏段、镜头列表，以及该任务已保存的每个事件和每个多帧分析窗口是否跨镜头。
- **对已有结果零影响、零费用。** 只读项目数据库（只读方式打开）、扫描前后各核对一次原片SHA256（中途被改就不出报告）；报告只能写到新文件，不能写进项目目录或原片所在目录；不改分析、排名或验收，不发任何模型请求。
- **真实例子（长钟馗15分52秒，任务5c7894aa…）**：18–21秒扫完；镜头切换41处、镜头50段、黑屏10段共34.6秒。469个已保存事件中7个跨越镜头切换、1个含黑屏；**272个多帧分析窗口中41个（约15%）把不同镜头的画面一起交给了模型**，18个含黑屏帧。被拒的3个窗口里，第21窗含2个镜头切换，第248、253窗没有——跨镜头不是那两次拒绝的原因。项目数据库哈希前后一致。
- **工作台里一键检测、直接看到。** 左侧“镜头切分（本机，不花钱）”卡片点“检测镜头切换”，约20秒后显示切换数、黑屏段、跨镜头事件／窗口数；时间轴上方画出切换刻度、下方标黑屏段，跨镜头的事件和单录像候选卡片显示“跨 N 个镜头切换”。报告缓存在仓库`.cache/workspace/shots/`（不进项目目录）；下次打开同一任务自动读缓存、不重新扫描；该任务的分析结果有变化（新事件、新窗口状态）或换了检测参数时缓存自动失效。内置浏览器实测：长钟馗41切换／7事件／41窗口，与命令行一致，重新载入后读缓存，无控制台和服务端错误。
- **每个重建窗口都核对过“确实是当时发给模型的那组图”。** 用保存的每个分析阶段输入哈希比对重建窗口的帧编号：长钟馗272窗全部已开始分析、0个不一致，因此“41窗跨镜头”说的就是实际发送的输入。
- **人工抽查**：90.4秒（过场里换机位）和585.5秒（实机战斗切到Boss登场过场，界面HUD消失）两处检测结果目视确认为真实切换。只抽查了2处，整体准确率未经人工评审。

## 二、怎么判定（启发式，参数随报告保存）

- FFmpeg一次解码（先缩到320×180）：`scdet`镜头变化分数>10记候选切换；`blackdetect`（像素阈0.10）记黑屏开始／结束。用`-copyts`和视频流自己的时间基换算到原片时钟，与媒体准备取帧完全同一换算（`MediaAsset.instant`），并逐条核对FFmpeg打印的秒数与整数时间戳一致，不一致即拒绝。
- 两个候选相隔<120毫秒视为“闪光”（进出一帧强光／暗帧）两个都丢；距上一个已接受切换<0.5秒的候选丢弃；落在黑屏段内或边缘的切换由黑屏边界代替；黑屏短于0.2秒不计。
- 事件“跨镜头”＝切换严格落在事件区间内（两端各留1毫秒，吸收事件边界与帧时刻各自取整的1微秒差）。窗口“跨镜头”＝切换落在窗口第一帧之后、最后一帧及之前。窗口按该任务保存的取帧时刻和它自己的窗口设置重建（`window_slices`，与实际发送窗口同一函数）；仅schema v2任务有窗口。

## 四、仍未知／不做的

- 准确率只抽查2处；游戏内快速运镜、爆闪、UI弹窗可能误报或漏报。阈值未用人评校准。
- 本项只**报告**跨镜头，不改分析窗口划分。若要让新分析按镜头切窗口，需要新的分析配置版本，属于将来的付费分析提案，不在本项。
- “闪光”规则会把相隔<120毫秒的两个候选都丢掉：真实硬切后紧跟一帧运动模糊也超阈值时，这次真实切换会漏掉（切换数可能偏少）。暂不改算法，记为已知限制。
- 验收就绪摘要在**手动分页**且当前页已有可检索运行时，不会列出别页覆盖缺口的A/B/D待决定（“部分快照”阻断仍显示；工作台和命令行默认读全部，不受影响）。
- 联合检索（多录像）候选卡片暂不显示跨镜头标签，只在单录像视图显示。
