# 工作台详情打开提速方案（TD005），完整核对保证不变

## 一、结论

推荐采用"单次完整核对 + 同一次请求内复用"方案，并吸收另外两个方案的几个做法。这个方案对完整性保证没有任何放宽：每次打开详情，仍然逐字节核对原视频和全部证据文件，也不新增任何跨请求的"信任缓存"。提速只来自去掉重复劳动，以及在测量证明有效后让核对并行进行。另外两个方案（NTFS 身份缓存、后台分级核对）这次不做。NTFS 身份缓存只作为以后可选的快速模式记录在案。

## 二、对用户来说有什么变化

- **打开详情更快。** 现在打开一个 15 分钟的任务约 1.7 秒。预计第一步之后约 1.0–1.3 秒，并行一步也生效的话约 0.6–0.8 秒。一小时素材现在预计 7–9 秒，会超过工作台首次 5 秒的等待。优化后在系统缓存已读过文件的情况下预计 2–2.5 秒。以上都是根据已有分项测量推算的，还没有实测。
- **搜索提速最明显。** 工作台每次搜索都会走"打开详情"这个接口。代码确认，现在一次搜索会把原视频和约 950 个证据文件完整核对两遍：一遍在 `ui/service.py:423`，另一遍在 `cli/main.py:461` → `load_searchable_timeline` → `load_completed_timeline`。改完后只核对一遍，这部分时间约减半。
- **能看到核对结果。** 详情页可以多一行小字，例如"已完整核对：14:03:21 · 955 个文件 · 469 MB · 用时 0.7 秒"。用户能直接看到这次打开确实逐字节核对过，而不是只能相信它做了。

## 三、仍然保证什么

- 每次打开详情、每次搜索都会完整计算原视频、清单和每个证据文件的 SHA-256，并和数据库里的值比对。任何一个字节变了都会拒绝，报 `storage.integrity`。报错代码和问题顺序都和现在一致。
- 完成分析、续跑准备、素材准备收尾、恢复、导出、验收冻结/绑定、基准测试和所有命令行入口，行为不变，照旧完整核对。
- 路径边界规则不变：先做文字检查（不允许绝对路径和 `..`），再 `resolve()`，最后检查文件是否在运行目录内。区别只是运行目录每次操作只解析一次，而不是每个文件都重新解析一次。

## 四、新增了哪些"信任"，在什么时候

- **跨请求：没有。** 不使用文件大小、修改时间、创建时间、NTFS 文件 ID 或 USN，也不留任何进程级或会话级缓存。下一次打开会重新完整核对。
- **同一次请求内：只有一处复用。** 搜索直接使用本请求刚刚完整核对过的时间线，不再隔几毫秒又核对一遍。这段"核对后到响应发出前"的空档现在本来就存在，并不是新增的。
  - 为防止两次打开数据库之间有写入，搜索时仍会读一次运行记录，要求重新读到的运行记录（StoredRun：运行ID、素材及其SHA-256、配置、配置哈希、状态、错误码）与已核对时间线的完全相同；这依赖“已完成运行不可再改写”（`_mutable`），唯一例外是恢复把它标为失败，会改变状态从而退回完整加载。（实施时运行记录没有updated_at字段，未比对更新时间。）任何一项不一致就退回现在的完整加载，不报错也不放行。
- **一个小改进。** 证据引用里记录的文件路径，改为直接用刚被核对的那个路径，不再单独再解析一次。这缩小了现有的"核对的文件和后来引用的文件不是同一次解析"的空隙。

## 五、界面显示

- 接口返回里加一个 `integrity` 块：`{mode: "full-sha256", checkedAt, filesHashed, bytesHashed, elapsedMs}`。它只描述真实完成的完整核对，永远不会出现"已核对"却没读字节的情况。
- 详情页头部显示一行灰色小字（见第二节）。核对失败时沿用现有的"媒体已更改"拒绝提示，不新增状态机或按钮。

## 六、工程部分

### 机制

改动都在基础设施层，外加应用层和 CLI 上的一个可选参数。领域层不动。

**第 A 步：低风险，先做**

1. `sqlite_store.py`
   - 新增 `_run_directory(run_id)`，每次操作只解析一次运行目录。
   - `_stored_artifact(run_id, path, *, run_directory=None)` 规则完全不变，只是复用这个已解析的目录。现在 `sqlite_store.py:716` 每个文件都会重算一次运行目录。
2. 把 `_integrity` 拆成两步：
   - `_integrity_plan(run_id)`：在存储线程里读数据库，做路径检查和 resolve，返回待核对清单、路径类问题，以及 `evidence_id → 已解析路径` 的对照表。
   - `_verify_plan(plan)`：核对字节，循环逻辑和现在一样。
   - `_integrity` 就是两步合起来，`complete_run`、`prepare_resume`、`finish_media_preparation`、`recover` 等调用方完全不变。
3. 每个证据文件只解析一次。现在 `load_timeline` 先经 `_consistent`/`_integrity` 解析一遍（第 1271 行），生成证据引用时又解析一遍（第 1428 行）。改为 `_consistent` 返回计划，`load_timeline` 按 `evidence_id` 从计划里取路径。证据查询有 `ORDER BY`，核对清单没有，所以必须按 ID 对应，不能按顺序对应。
4. 请求内复用
   - `execute_search(..., verified_timeline: StoredTimeline | None = None)`，只能用关键字传入。
   - 传入时仍打开写入用的数据库，因为 `persist_search` 和保存搜索 JSON 照常执行。只调用很轻的 `store.load_run(run_id)`，再调 `refuse_unsearchable_run`，并比对运行 ID、完成状态、原视频 sha256 。不一致就退回 `load_searchable_timeline`。（实施版比对整条StoredRun，无updated_at字段）
   - `inspect_run` 只在运行状态为 COMPLETED 时传入。
5. 在 `application/storage.py` 的 `StoredTimeline` 上加 `integrity: IntegritySummary | None = None`。它是纯数据，默认值保证现有测试替身不受影响。`view_payload`/`inspect_run` 输出这个块，`ui/static/app.js` 显示那行小字。

**第 B 步：有条件，A 实测后再决定**

- 用标准库的有界 `ThreadPoolExecutor`，只并行"打开 + 哈希"。`resolve()` 和路径边界检查仍留在存储线程，采纳评审意见，避免路径检查进入多线程。
- 原视频单独一个任务，证据按每批约 64 个分批。结果按原顺序返回，保证问题列表顺序一致。每次加载的所有任务都在 `finally` 里收尾，不留未关闭的文件句柄，避免再出现 TD012 那类锁问题。
- 线程数可通过已有的设置或环境变量配置，设为 1 就是串行，用于机械硬盘或测试。
- **启用门槛：** 在 15 分钟真实任务上，如果证据核对时间下降不到 30%，就不合入，只在 TD005 里记录结论。评审指出，NTFS 方案的探测显示打开加查询 954 个文件只要约 0.04 秒，说明瓶颈可能在读取或 Defender 扫描，而不在打开文件本身，所以并行收益还没有证明。

**第 C 步：只改文档和一个固定现状的测试**

- TD008 补写实测事实：工具链固定的 CPython 3.13.16 在 Windows 上，`st_ctime_ns` 是创建时间。因此 `ui/media.py:67-73` 的签名 `(dev, ino, size, mtime, ctime)` 发现不了"同大小原地改写后恢复 mtime"。加一个仅在 Windows 上运行的测试固定这个现状，不宣称已解决。
- 把 NTFS 身份快速模式（USN + 128 位文件 ID + ChangeTime + 禁止写入的打开方式）记为未来可选项。前提：业主明确授权、默认关闭、有信任时长上限、永不用于验收/基准/状态转换，并且需要单独的 ADR 和 opus 审查。

### 已知限制

- 系统缓存没读过文件、或素材在机械硬盘/U 盘上时，读盘速度决定一切，一小时素材可能仍要 10 秒左右，这里不承诺提速。
- 单个文件的 SHA-256 不能并行，原视频哈希时间（1.5–2 GB 约 1.2–1.6 秒）是速度下限。
- 本地没有真实的一小时素材，一小时的数字都是推算。

## 实施记录（2026-10-25，第A步）

实测发现第三处重复：`persist_search`保存检索记录前的`_consistent()`又完整哈希一遍，所以带查询的一次打开原为每文件3次哈希（不是方案估计的2次）。第A步实现：①运行目录每次操作只解析一次；②`load_timeline`的证据引用直接复用刚哈希过的路径；③`execute_search`在调用方同一请求刚完整核对、且重新读取的运行记录完全相同时复用该时间线，否则完整重载；④`execute_search`保存检索记录时只重做数据库一致性检查、不再重复哈希（其他调用者不变）。之后任何一次打开仍逐字节完整核对。测量：每文件哈希次数3→1；演示项目副本（111证据）无查询0.24→0.17秒、词法检索0.85→0.21秒、混合检索3.77→约2.7秒（余下主要为本地向量模型）；真实钟馗15分钟任务打开约1.7（波动至3.2）→约1.0秒。新增5项测试，相关31个测试文件1248项通过。第B步（并行哈希）与界面“已核对”小字未做，后者属业主决定事项。

## 第B步决策用测量（2026-10-25第三会话，只读，未改代码）

真实钟馗15分钟任务（原片406MiB＋953证据帧，`artifacts/td005-real-long-20261025/project`），只读SHA-256，同一机器空闲、文件已在系统缓存（热缓存），每组5次取中位数：

| 范围 | 1线程 | 2线程 | 4线程 | 8线程 |
| --- | --- | --- | --- | --- |
| 全部文件 | 1.144秒 | 0.816秒 | 0.672秒 | 0.746秒 |
| 仅证据帧 | 0.443秒 | 0.589秒 | 0.516秒 | 0.399秒 |

结论：4线程使完整核对下降约41%，超过方案的30%门槛；但收益几乎全部来自“大原片与小证据帧同时算”，证据帧本身并行没有收益。冷缓存（首次打开、慢盘）未测，可能主要受磁盘限制。是否做第B步仍由业主决定（见第七节①③）；若做，较简单的形状是“原片单独一个线程＋其余顺序”，不必通用线程池。测量脚本只在会话临时目录，未入库。
