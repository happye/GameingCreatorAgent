GamingCreator 人机协作复盘

数据来自 8 个方向的只读审计（规则、文档与交接、Git、测试、缓存、代码、记忆、人机流程），每个方向的结论都由另一个 Agent 重新取数、反驳和修正，最后再做一次查漏。文中数字已采用修正后的值。审计期间仓库里另一个 Agent 仍在提交，所以个别计数会小幅变动。

总体结论：产品做出来了，但协作流程本身变成了最大的工作量。
高效：不达标 整洁：不达标 可复用：部分达标

这 29 天里 Agent 写了约 5 万行源码、6.5 万行测试，做出了分析、检索、渲染、字幕、发布包、桌面 EXE 和安装包。但同一时期：

  • 44% 的提交一行代码都没改，只在更新记录文档；
  • HANDOFF.md 被 78% 的提交改过，几份记录文档累计改动的文字量约为源码的 40%；
  • 新会话按规则要先读约 74 KB 才能开工，加上按需读的部分可达 184 KB；
  • 约 78% 的源码写于第一个"创作"功能之前，都在为一道还没人去做的人工验收关口添砖加瓦。

问题不在于你用了 Agent，也不在于某一条规则。主要原因是：每次不满意就追加一条"永久规则"，规则只写成文字、没有工具去执行，所有东西都只增不删，而你主要通过 Agent 的汇报来判断进度。这四点叠在一起，Agent 就会把"遵守流程、记录流程、证明自己没越界"当成主要任务。

值得保留的部分也很明确：不碰素材和密钥、付费调用前要授权、保留原始证据，这些边界一直守住了；把"实现完成、质量验收、商用发布"分开记录的思路是对的；仓库从未提交过视频或数据库，打包后只有 2.9 MiB。

四个根因

下面这些表面问题很多，但几乎都能归到四个原因上。先治这四个，大部分表面问题会自己消失。

根因 1：没有"唯一事实源"，却要求手工同步 7 份文档

AGENTS.md 的"Persistent progress board"和"progress alignment"两节规定：每次"重大改动"后，要在同一次提交里同步看板、HANDOFF、sprint、progress、assignments、human-inputs、tech-debt。规则没有定义什么才算"重大"，Agent 就每次都照做。另一条要求"记录推送状态和提交号"，而一次提交不可能包含自己的哈希，于是每次代码提交后必然跟一次补记提交。

直接后果：提交数翻倍、44% 的提交只改文档、174 个脚本里有 47 个专门改这些文档。7 份文件里的数字已经互相打架：current-status.md 写 38%，看板写 60%，grok-task-list.md 写技术债 12/4/5，看板写 14/2/5。

根因 2：规则靠"出一次问题加一段话"堆起来，只有文字，没有机制

AGENTS.md 后半部分是 6 段"Persistent …"，每段都以"用户于 10-xx 明确要求"开头。汇报规则在 6 个文件里重复出现，看板规则在 7 个文件里重复出现。规则从来只加不删，也几乎没有变成脚本、钩子或测试，Agent 只能每次读一遍、自己理解、自己证明遵守了。

直接后果：每个会话自动加载 19 KB 规则，再读 50 KB 以上交接文档；文档里 516 处免责句；提交信息里塞满"0 费用""不宣称 F006"。

根因 3：所有东西都只增不删

.learnings 累计新增 689 行、删除 2 行；测试新增 6.67 万行、删除 881 行；进度日志、sprint、报告、分支（88 个）、prompt 版本（6 版 vision prompt 都还能执行）、缓存目录也都在累积。没有任何规则规定"什么时候删""试点结束后谁胜出"。另一方面，保护用户数据的规则又写得很宽（"永远不要回收证据"），而证据和垃圾混放在 .cache 里，Agent 最安全的选择就是什么都不删。

根因 4：你看到的是汇报，不是产品；人工关口没有时限

你的工作方式是"给目标，看最终汇报，再给下一个目标"。规则要求每次关键改动后都写一份详细的通俗汇报，并附上看板数字，于是 Agent 把力气放在让汇报显得完整、让数字上涨。Phase 0 的"Top-10 可用率 ≥70%"需要你亲自评，但这个关口没有截止时间，Agent 拿不到你的评分，就在它能推进的方向上不断加码：做了 8 步验收工具（登记、冻结、绑定、复核、评分……），实际执行次数却是 0/8。10-30 取消全局关口之后，又直接把 51 项全部铺开，三天里 41 项变成了"部分完成"，但没有一项通过验收。

你点名的问题：核实结果

.cache 里上千个"小版本备份"目录

属实，但大多数不是备份，而是三类垃圾混在一起：

  • 测试临时目录：verify.ps1 第 15 行每次运行都新建 .cache/pytest-runs/<GUID>，脚本里没有删除逻辑。10-31 补的清理钩子判断条件写错了，对 verify 的目录永远不生效。已经有 186 个，最新一个里面残留 2,084 个子目录。还有 66 个 pytest-*、35 个 td015-*、23 个 pytest 缓存变体，都是 Agent 每次临时起的新名字。
  • 一次性改文件脚本：174 个 _*.py，再加约 80 个 patch_*、record_*、write_* 脚本，全部产生在 10-22 和 11-01 两天。它们大多是用 Python 去替换文档里的提交号、追加 sprint 记录、修改测试，绕开 Windows PowerShell 下编辑中文多行文本时的引号和编码问题。
  • 被锁住的目录：38 个顶层目录当前用户没有读取权限，推测是 Codex 沙箱用另一个 Windows 账户创建的。最早换新目录名，就是为了绕开这个锁（.learnings/ERRORS.md 389–423 行）。

为了绕开 Windows 文件锁，选了"每次换新名字"而不是修锁；同时 .cache 里还混放着用户作品（workspace/creations 409 MB）、模型和验收证据（受 Git 管理的文档引用了 304 个 .cache 路径），Agent 不敢动。

规定 .cache 里的内容随时可以整体删除；用户作品、模型和证据摘要先迁走。verify 改用固定目录，并在结束时清理。一次性脚本只能放在 .cache/scratch/，会话结束时删除。被锁目录由你用管理员权限单独处理（只处理那 38 个，不要对整个 .cache 重置权限）。

提交过于频繁

属实，而且主要由规则造成，不是 Agent 的习惯。今天 15:03 到 16:01 的一小时里完成了 T15 到 T28 共 14 个"任务"，每个间隔 3 到 8 分钟，每个都同时改 7 份记录文件，前几个还各跟一条补记提交。紧接着另一个 Agent 又以每 8 分钟一次的节奏提交 TD004 别名词表微调。

上面说的"同提交同步 7 份文档 + 记录自己的提交号"，加上"每个实现/验证节点更新 sprint"（agent-workflow.md:71），就会产生"一个小改动 = 一个任务卡 = 一次提交 = 一次推送 = 一次补记"的循环。推送有 219 次，但仓库没有 CI，推送并不会触发任何验证。

一次提交对应一个用户能感知的能力或一个缺陷修复；记录写在提交信息里，git log 就是变更日志。禁止"记录本次提交号"这种补记提交。状态文档只在里程碑结束或会话结束时更新一次。推送时机改为里程碑完成、会话结束、长任务开始前。

不管改了什么都跑全量测试

基本属实，但要说准确：10-22 那种 54 秒一次的提交不可能每次都跑 24 分钟的全量。实际情况是：没有"改动对应哪些测试"的机制，Agent 要么手写一串文件名凭感觉挑，要么在每个交付节点跑一次全量来"自证"。有记录的 verify 调用约 125 次，按每次 15 到 24 分钟算，合计远超几十个小时。

  • 自定义标记只有一个 media，只用在 1 个文件上；而 42 个文件、12,130 行测试会启动真实 Chromium，49 个文件调用 FFmpeg。
  • verify 每次还会对 3,309 个 Python 运行时文件逐一算哈希，并做两次 wheel 可复现构建。这是发布前该做的检查，被放进了日常验证。
  • pytest 缓存每次都换新目录或直接禁用，所以 --lf（只重跑上次失败的）一直用不了，失败后只能重跑整套。
  • testing-guide.md 的前 33 行是历次运行记录，真正讲怎么跑测试的内容从第 35 行才开始。

测试分三层。迭代时只跑受影响的文件，并排除浏览器和真实数据测试，目标 1 分钟以内。合并或里程碑时跑全量，用 pytest-xdist 按文件并行，预计 6 到 8 分钟。CI 在 push 时跑离线子集。在 conftest.py 里按 import 自动打 browser、media、local_data 标记；已知失败用带技术债编号的 xfail 隔离，不必每次再人工比对"是不是还是那几个旧失败"。

文档臃肿、层级混乱，新会话要花大量上下文回顾

属实。不过问题不在目录太深（最深只有 3 层），而在文件太多、入口太多、同一件事写了太多遍。

  • docs/exec-plans 一个目录下平铺了 333 个文件：252 个 sprint、53 个报告、9 个历史文件。
  • HANDOFF.md 本该是"覆盖式快照"，现在顶部是 35 条按日期追加的流水，其中 31 条写着"计数不变"，真正的现状段落在第 79 行。
  • CLAUDE、AGENTS、agent-workflow、grok-task-list 各自规定了一套"先读什么"。Claude 会话的硬性必读约 74 KB，再加 feature_list.json（67 KB，单个 F010 条目就有 74 条证据）和总方案，要 120 到 184 KB。
  • README.md 是 28 KB 的英文功能流水账，最后更新于 10-30，完全没有提到 11-01 交付的 EXE 和安装包。它还把读者引向数据已经过时的 current-status.md。

必读预算定为 15 KB：AGENTS.md 不超过 6 KB，STATUS.md 不超过 5 KB 且只覆盖写，当前任务卡不超过 3 KB，各工具入口只保留差异部分。看板数字由脚本生成。feature_list.json 改为按编号查询，不再整份读。历史类文件全部移入 docs/archive/，并从默认搜索中排除。

长周期下的代码堆积与过度设计

属实，最明显的在 10-22。那天 retrieval.py 被提交 45 次，从 911 行涨到 2,436 行，其中 27 次是"加固"（deepen、gate、contract）。最长的函数 assert_project_search_document_contract 有 487 行。retrieval.py 约 37%、detail_query.py 约 61% 的代码是合同断言，用来防"本地自己生成的 JSON 被篡改"。

  • 版本泛滥：166 个 -vN 标识、13 种回执格式，6 版 vision prompt 都还能执行。
  • 多条方案并行、没有收口：主体细节检索留下 5 套实现，没有一套通过 F010。
  • 重复造轮子：19 个文件各写一套严格 JSON 读取，20 个文件里有 32 个私有的错误构造函数。
  • 巨型分派函数：CLI 的 _dispatch 306 行，HTTP 服务的 do_POST 470 行。

"保留身份、来源、费用"这些原则没有写明"做到哪一步为止"；评审 Agent 每找出一个新的边界情况，就会变成一次加固提交。没有复杂度上限，也没有"试点结束后删除落选方案"的规则。

加一条设计预算规则：本地自产数据只校验格式版本加一个整体哈希，只有付费调用、费用账本和原始证据绑定才做深度校验；单个合同函数不超过 80 行；同一文件一天内有 5 次以上加固提交，就停下来写技术债。ruff 打开 C901 和 PLR0915 两个复杂度检查，旧文件先豁免。每个试点结束时写一页 ADR 宣布胜出方案，落选方案在同一个改动里删除。

新发现的问题

进度看板在测量"动作"，不是"交付"

看板的公式是"已交付 = 1、部分 = 0.5"，给任何一项加一点实现，它就从"未开始"变成"部分"。10-29 是 27%，10-30 是 32%，现在是 60%，但已交付一直是 10 项，第一个可用产品是 0/22。从 T1 到 T27，HANDOFF 里一直写着同样的数字"10/41/0"。看板第 1 节里"正式 Windows EXE"仍是未完成，而 EXE 和安装包已经交付；第 6 节的"刚完成"还停在 T7。

主指标改成 3 到 5 条端到端用户流程，例如"导入录像 → 得到一条可发布的 1 分钟玩法展示视频"：是否跑通、耗时多久、要人工干预几次、最近一次实际演示的日期。功能清单改为附表，状态分成骨架、可用、已验收三级，全部由脚本生成。

费用防护和实际花费严重不成比例

到目前为止实际花了 ¥1.49，记录过的最高单次任务上限是 ¥5。围绕费用建了账本、预留额度、人工零扣费确认、回执校验等多层机制，代码约 1,950 行；一笔"¥4.065536"（两次未扣费的 HTTP 400）在 67 个文件里出现了 122 次。

费用保护要保留（见"必须保留的保护"），但可以由你决定改成"周期预授权"：例如每月 ¥20 以内、只分析 GameVideos/ 里你自己的素材，超额再逐次申请。金额只记在一个账本文件里，交接文档只引用总额。

自己给自己加的环境限制：pyc 回执校验和"一律 -B"

工具链校验把 3,309 个 Python 运行时文件全部算哈希，连 .pyc 也算在内。但 .pyc 是 Python 正常运行时会自动重写的缓存，于是"正常运行"被判成"被篡改"，同样的事故发生了 4 次。之后的补救不是修改校验范围，而是给所有 Agent 加一条"Python 一律带 -B"的纪律，这条纪律写进了 15 份指南和 Claude 记忆，Codex 和 Grok 的子 Agent 仍会漏掉。

校验排除 __pycache__，或者只校验 exe、dll 和安装归档；日常 verify 不做这项检查，只在 setup 和 build-app 时做。修好后删除"一律 -B"这条规则。

学习记录只写不读

.learnings 有 72 KB，但 AGENTS、CLAUDE、CODEX、grok 的入口规则都没有引用它，引用它的地方全是"要往里写"的义务。同类错误反复出现：pyc 漂移 4 次，猜路径或猜锚点 18 次。另外装了两个功能重叠的自我改进技能，触发条件都是"命令失败就记录"，琐碎失误也会被写进去。

同一类问题出现第二次，就必须改成脚本、测试或检查规则；做不到的，只在 AGENTS.md 的"已知坑"里留一行（总数不超过 10 行）。已解决的条目移入归档。两个自我改进技能只保留一个。

分支和工作树残留

本地有 88 个分支，其中 43 个是 10-31 退役工作树时留的快照分支，40 个与 main 内容不同。整个历史没有一次合并提交，git 已经无法判断哪些分支已经集成。.worktrees 下还有 8 个没有 .git 的源码副本。

先用 git bundle 把这些快照分支打包到仓库外并验证，再删除分支。写一个退役工作树的脚本，按"检查未提交改动 → 删除 junction → git worktree remove → 删除分支"的顺序执行，取代现在的文字说明。

多工具协同成本高，收益低

实际协作几乎是"额度用完就换工具"的顺序接力，并没有真正并行，但仓库为此维护了 9 个 Claude 角色、18 个 Codex 角色配置（其中 9 个尚未提交，命名还和已有的 9 个不同）、3 份路由指南、30 个提到 DSH 的文件，还有"另一个工具在写时不能动主树"之类的协调规则。现在就有一个例子：本次审计期间，另一个 Agent 在主树上留下了未提交的 retrieval.py 改动，并且一直在提交。

明确协作模式是"同一时刻只有一个写者的顺序接力"。角色只保留探索、实现、审查 3 个，所有工具共用一份定义。交接只靠 STATUS.md 加任务卡。

没有 CI，"测试通过"全靠 Agent 自己说

.github/workflows 只有一个空的 .gitkeep，也没有 git hook。"测试全绿"的唯一依据是 Agent 自己的会话输出，所以又衍生出"原始日志保留""不得称全绿"等大量措辞规则，文档里还引用着已被 Git 忽略的 .cache/*.xml 作为证据。

在 GitHub Actions 加一个 windows-latest 工作流，push 时跑 lint、mypy 和离线测试，不放付费 API 密钥，不访问素材。之后交接里只需写"CI 第 N 次运行通过"。

需要你做的事太重，也太分散

人工验收被设计成 8 步流程（每个主查询至少 10 个事件，前 10 名逐项打 0 到 3 分并写理由），但事先没有估算你要花多少时间。像 TD005（4 线程哈希）这样的技术取舍也被推给你决定。第三方许可证缺口（FFmpeg GPL、模型权重能否分发）写在 human-inputs.md 第 3 行的段落里，却没有进入待办计数，看板和 HANDOFF 都写着"现在必须做的 0 项"。

每个人工请求只写一行：做什么、预计几分钟、入口在哪、什么时候要。总量超过 60 分钟就先缩小范围。技术取舍由 Agent 自己决定并记录。许可证缺口应补成正式待办行（阻断分发和商用，不阻断开发）。

问题一：上下文到 70% 就收尾开新会话，对吗？

方向是对的，但在这个项目里，你为此付出的代价被规则放大了好几倍。

对的地方：上下文越长，模型对前面细节的注意力越弱；自动压缩也会丢掉细节。在一个阶段性的节点主动换会话，比等它被动压缩更可控。

代价被放大的地方：

  • 收尾很贵。规则要求收尾时同步 7 份文档、写详细汇报、附看板数字，一次收尾就要消耗不少上下文和时间。
  • 开头也很贵。新会话按规则先读 74 到 184 KB，粗略估算 3 万到 7 万 token。对 20 万 token 的窗口来说，相当于一开局就用掉 15% 到 35%，到 70% 时又要收尾，真正干活的空间只剩一半左右。
  • 按比例切，而不是按任务切。到 70% 时任务往往做了一半，于是要写"中途状态"，新会话再花力气重建上下文。
建议的做法
  1. 先把交接做轻：必读不超过 15 KB，交接时只覆盖写一份不超过 5 KB 的 STATUS.md。交接便宜了，换会话才划算。
  2. 按任务边界换会话，而不是按百分比：一个会话做完一个能演示的切片就结束，哪怕只用了 40%。如果任务进行到一半时到了 70%，在 Claude Code 里可以手动执行 /compact 保留：当前任务目标、已改文件、下一步，在原会话里继续，不必写交接。
  3. 中途状态放进 git，不放进文档：未完成的工作提交到本地 WIP 分支，任务卡写一行"继续 X"，新会话执行 git log -5 和 git diff main 就能接上。
  4. 大范围阅读交给子 Agent：让子 Agent 去读文件、跑测试，只把结论带回主会话，主会话的上下文就涨得慢。项目里已经有 gc-explorer 和 gc-runner 这类角色，用对场景即可。
  5. 禁止新会话"回顾历史"：明确告诉 Agent 不要读 progress.md 和历史文件，现状以 STATUS.md 和 git log 为准。

问题二：总方案里的技术细节是否限制了 AI？

总方案本身写得相当克制，问题主要不是"细节太多"，而是"原则没有写代价和边界"，以及"关口没有写时限"。

总方案里有很多值得肯定的地方：第 57 节列出了"V0.1 不应该开发的东西"，第 58 节说第一版甚至不需要 GUI，第 8 节说"第一阶段绝对不要同时做全部模式"，第 70 节要求 Agent 先做反向审查。本地优先、FFmpeg 负责执行、AI 只输出结构化决策，这些架构原则后来也被证明是对的。

真正让 Agent 做了大量无用功的，是下面三点：

1. 原则写成"必须"，但没写"做到什么程度为止"

第 69 节写了"Prompt 必须版本化""模型成本必须可观测""平台规则不得硬编码""用户修改行为必须被记录"。Agent 会把每一条都做到极致：166 个版本号、13 种回执、为 ¥1.49 的花费写了约 1,950 行账本代码。

2. 关口需要你亲自评，却没有时限

第 59 节和第 71 节规定，"Top-10 可用率 ≥70%"通过之前不进入下一阶段，而且这一项必须由你评。你没时间评的那 25 天里，Agent 没法推进主线，只能在关口周围加码。约 78% 的源码写于第一个创作功能之前。

3. 大分母被拿来当进度

总方案描述的是最终形态（72 节、7 种模式、商业化分级）。10-30 之后，它被翻译成"51 项全部推进"，并作为看板分母，结果 3 天里 41 项变成了"部分完成"。这正好违背了总方案自己写的"第一阶段绝对不要同时做全部模式"。

4. 有没有堵住更好的方向？

有一处比较明显：总方案说 Phase 0 只要 CLI 加检索，但没有说"先用最便宜的办法看效果"。结果在花钱验证之前，就先搭好了冻结、绑定、复核等完整的验收流水线。更好的路径是：先花 30 分钟拿 1 个查询看前 10 名，再决定要不要投入工具。

下一份方案可以这样写
  • 第一层：不可变的目标和边界（不超过 1 页）：给谁用、解决什么问题、哪些事绝对不做、费用和素材红线。
  • 第二层：验收方式和时间盒：每个阶段用什么判断成败、谁来判断、最晚什么时候判断；超过时限怎么办（例如降级为并行质量线，继续往下做）。
  • 第三层：技术建议，明确标注"可推翻"：Agent 可以提出更好的方案，写一页 ADR 说明理由即可替换。
  • 每条原则都写上"够用的标准"，例如"成本可观测＝每次调用记录模型、token 和估算金额，写进一个账本文件即可"。
  • 写一个复杂度预算，例如"Phase 0 源码不超过 1 万行；超过就要停下来复盘"。

双视角建议

站在 Agent 的角度：什么让它高效

  • 开局轻：自动加载的规则越短越好，一句话说清"现在做什么、做完的标准是什么"。
  • 只有一个事实源：遇到两份互相矛盾的文档，Agent 会花大量 token 交叉核对，甚至重做已完成的工作。
  • 规则能被执行，而不是只能被理解：钩子、脚本、lint、CI 比一段话可靠得多，Agent 也不需要每次自证。
  • 明确允许删除：说清楚哪些东西可以随时删，否则谨慎的 Agent 一定选择保留。
  • 有清楚的"完成"定义和停止条件：没有终点的任务，会被各种加固、诊断和补充测试填满。
  • 反馈要快：1 分钟出结果的定向测试，比 24 分钟的全量更能让它小步走对。

站在你的角度：你的时间花在哪里最值

  • 看产品，不看汇报：每个里程碑让 Agent 给你一个能打开、能播放的东西，再加 3 行说明，你花 10 分钟实际用一下。
  • 人工关口要早做、做小、限时：第一次只评 1 个查询的前 10 名，30 分钟以内；Agent 要事先告诉你需要多少分钟。
  • 先改工具，再加规则：想加一条规则时，先问"能不能用脚本或检查实现"。规则总数设上限，加一条就要合并或删除一条（安全类规则除外）。
  • 每周 30 分钟整理：删除过时规则、归档文档、清理缓存和分支，相当于定期还技术债。
  • 少换工具：每换一次工具都要重新付一次交接成本，而且多一套适配配置。尽量固定一个主工具，其他工具只做独立的旁路任务。
  • 汇报要短：每个里程碑一段 150 字以内，写"现在能做什么、下一步是什么"，中途不必汇报。
