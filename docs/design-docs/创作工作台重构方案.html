创作工作台重构方案

依据你的《V0.1 工程协作体系优化与 UI/UX 专业化升级》要求和 J1 第二次试看反馈。按要求，这一轮只做审计和方案，不大规模改代码。每条结论都注明依据：代码表示读过源码或实测；文档表示来自历史文档；判断是我的工程判断。

先回答你的 8 个问题

0. 素材工作台和创作视频是什么关系？片段篮有什么用？

代码现在是两个互不相通的页面：

  • 素材工作台（首页）：看分析结果、预览原片、查看证据帧、一句话检索片段，并把片段加入片段篮。
  • 片段篮：只能下载 JSON 或 CSV 区间清单，创作页读不到它。
  • 创作页：只能整段勾选录像，交给规划器从全部事件里挑片。

所以你的理解没错：放进片段篮的东西，在创作视频里用不上。不过规划器内部已经支持“只用指定的事件”（candidates(timelines, event_ids)，命令行在用），只是网页接口没开放。

合并成一个工作台。素材检索的结果可以“加入创作”，作为必选或候选片段直接交给规划器；首页不再是一个独立的“上级页面”。

1. 选方案时能看视频吗？先出方案还是先出视频？

代码先出方案，再出视频。方案只是一张剪辑清单（每段来自哪段录像的第几秒到第几秒），几乎不花时间；视频只在你点“生成视频”后才用 FFmpeg 渲染，60 秒成片约一分钟。所以目前选方案时只能看文字。

判断两种做法各有问题：先渲染再给你看，会白白花掉很多时间；只给文字，又看不出效果。第三种做法更好：即时预览，不渲染。

  • 播放器按方案的剪辑清单，在原片（或已有的 360p 代理文件）里跳着播放，点“预览”立刻能看。
  • 每个镜头用已有的分析证据帧做缩略图，方案以“胶片条”形式展示，不再用大段文字。

代码这两样素材都已经存在：/api/media?proxy=1 支持分段读取代理视频，/api/evidence 提供每个事件的采样帧。只有点“导出成片”时才真正渲染。

2. 配乐要自己上传吗？会自己裁剪吗？

代码不会生成音乐，只能用自己的曲子，而且只能用命令行脚本 register-music.ps1 登记，页面上没有上传入口。

  • 成片里，配乐从歌曲开头开始放，循环到视频结束再截断。
  • 可以调音量，可以在原声响起时自动压低配乐。
  • 不能选从哪一段开始，结尾也没有淡出。

判断我同意现在不做 AI 生成音乐。要做的是：

  • 页面上可以直接拖入本地音乐；
  • 可以选择从歌曲哪一段开始，结尾自动淡出；
  • 以后加本地节拍检测，让镜头切换对上鼓点。节拍检测是信号处理，不需要 AI 去“理解”音乐，在本机就能跑。

3. 旁白用的是什么接口？免费吗？有次数限制吗？

代码用的是 Windows 自带的语音合成（SAPI，scripts/sapi-narration.ps1）。完全本地，免费，没有次数限制，但音色就是系统朗读的声音，你听到的“很差”正是它的上限。

换成接近真人的语音模型，并做成可替换的“语音提供方”。有两条路：

  • 云端语音服务：效果稳定，按字数付费。
  • 本地开源模型：免费，但需要较好的显卡，安装也更重。

建议先用同一段稿子，生成 2 到 3 家的样音，你靠耳朵选。各家的具体价格和条款，我会在试听方案里查实后再列出来，不凭印象写。云端调用会产生费用，按现有规则，需要你批准一个具体方案后才会调用。

4. 3 分钟口播配 40 秒画面会怎样？“挂接旁白”是什么？

代码你判断得对：

  • 会被截断。混音时把旁白截到视频长度（atrim=end_sample=total），页面只显示一条“超出”提示。
  • “挂接旁白”的意思是：把已经生成的那条旁白音频，指定给某个剪辑版本，并设置从第几秒开始播放。
  • 3 分钟视频目前只能手动把目标秒数填成 180，而且旁白和画面长度互相不管。

判断增加“口播优先”模式，流程是：

  • 先写稿，生成语音，得到准确时长；
  • 成片长度就等于旁白长度，规划器按这个长度挑片；
  • 还可以按段落对齐：稿子每一段对应一组镜头。

素材不够长时（例如只有一段 95 秒的录像），明确告诉你还差多少秒，而不是悄悄截断。“挂接”这一步会变成时间轴上一条看得见的旁白轨，不再需要单独操作。

5、6. 一句话改镜头、逐个调镜头，没有预览就没有意义

代码同意。这两个功能现在只是编辑一张文字清单，改完要渲染后才看得到效果，而且列表展开后会堆在页面最底部。

这两项功能都改到“时间轴加预览窗”里：

  • 逐个调镜头：镜头以缩略图排在时间轴上。点中一个镜头，右侧检查器显示它的裁剪、替换、速度、转场，预览窗马上播放修改后的效果。
  • 一句话改镜头：放进创作助手的输入框。改动先在时间轴上高亮显示“将要怎么变”，你确认后才生效。

7. UI 太老太土，需要重构

同意。具体方案见下面第四、五节。简单说，就是做成一个类似剪辑软件的单窗口工作台：

  • 深色专业配色；
  • 素材、剪辑、发布三个工作区；
  • 中间是预览窗和时间轴，右侧是随选中内容变化的检查器；
  • 创作助手融入工作台，不是一个孤立的聊天窗。

二、现有核心功能，以及重构时最容易弄坏的地方

代码现有功能：

  • 后端约 50 个 HTTP 接口，加上创作类的任务接口（方案、剪辑版本、渲染、旁白、封面文案、平台预览包）。
  • 前端是两个原生 JS 大文件：app.js 3,202 行，creation.js 1,084 行；没有框架，也没有构建步骤。
  • 桌面 EXE 用 WebView2 加载同一个本地服务。
容易被 UI 重构弄坏的依赖为什么危险
请求幂等 requestId（同一意图复用同一个 ID）弄丢它，重复点击就会创建重复任务，渲染还会被重复计费或计次
剪辑版本保存时带的 expectedParentReceiptSha256 等回执哈希后端靠它拒绝基于旧版本的修改；新 UI 必须原样传回
防串台计数 state.epoch / state.view切换项目或任务时，用它丢弃迟到的旧响应；新的状态管理必须有等价机制
任务轮询与崩溃恢复（pending/running → interrupted）后端负责恢复，前端只需继续轮询；不能改成“看起来完成就算完成”
付费分析入口、发送门禁工作台合并后，不能让一个按钮在未授权时触发付费视觉分析
本机草稿 creation-draft-v1、项目记忆 creation-workspace-v1新 UI 要能读取旧键，否则用户的草稿会丢

三、怎样用最少的约束，换到足够可靠的保护

  • 一份接口契约，而不是一堆文档。直接从 server.py 生成接口清单和请求字段；CI 比对这份清单，接口被删或被改名时报错。
  • 5 条真实端到端流程，取代逐个元素的模拟测试：
    • 录像 → 方案 → 渲染 → MP4
    • 修改镜头 → 保存版本 → 重新渲染
    • 旁白 → 混音
    • 封面文案 → 平台预览包
    • 检索 → 片段加入创作
    每条流程用真实服务器加 demo-phase0，断言产物：时长、帧数、回执、文件，不断言按钮文字。
  • 新旧并存，有回退路径。新工作台先挂在 /studio，旧页面保留到新页面功能齐全。再删旧页面时，连同它们的模拟测试一起删除。
  • 按风险决定验证深度：
    • 纯视觉改动：看一眼截图；
    • 面板与状态改动：跑受影响的测试；
    • 接口、时间轴、渲染相关改动：跑那 5 条端到端流程。

四、现有 UI 的主要架构问题

  • 代码按“功能”堆面板，而不是按“创作流程”组织。创作页上排着活动规则、知识、套餐、团队、反馈、配乐、旁白、一句话改镜头、逐镜头编辑，都是同一层级的面板。
  • 代码没有“预览即反馈”。方案、修改、旁白、配乐都只能渲染后才看得到效果。这是你第 1、5、6 点的根本原因。
  • 代码两个工作台之间数据不通：片段篮和创作是割裂的。
  • 代码巨型命令式脚本。一个 1,000 行的立即执行函数，直接改 DOM，状态散落在全局对象里。加任何面板都只能“往页面里 append”，所以位置混乱。
  • 判断值得保留的部分：
    • 后端任务模型：可恢复、幂等、有回执；
    • 证据帧与代理视频；
    • 渲染与校验；
    • 本次新做的规划器（时长达标、连续镜头）；
    • 草稿自动保存。
    适合重做的部分：全部前端布局、视觉、状态管理。

为什么是这个结构

  • 按创作流程组织。三个工作区对应三个阶段：素材（分析、检索、挑片）→ 剪辑（方案、时间轴、配乐、旁白）→ 发布（封面、文案、平台包）。这和剪辑软件按页面分阶段是同一个思路。
  • 空间固定，内容随上下文变。新功能不再往页面底部 append，而是出现在检查器或时间轴的对应位置，所以不会再有布局跳动和无限长的页面。
  • Agent 原生。创作助手的规划、执行状态和中间产物（方案胶片条、将要发生的改动）都直接显示在时间轴和预览窗里，不是一个孤立的聊天窗。
  • 即时预览让所有编辑有意义。这是解决你第 1、5、6 点的关键，而且不需要新增后端处理，素材都已经有了。

前端技术选型（三个方案）

方案做法评价
A 原生 JS 拆模块保留现有写法，拆成 ES 模块，加设计令牌改动最小，但很难做好时间轴和检查器这类联动界面
B 轻量组件框架，免构建（推荐）把 Preact + htm（约 15 KB）作为固定版本、带哈希校验的文件放进仓库，用 ES 模块加一个统一状态库；不需要 npm 和构建步骤有组件和统一状态，适合做工作台；符合项目“离线、隔离、不装全局工具”的约束；桌面 EXE 也能直接用
C React + 构建工具引入 Node 工具链和打包流程生态最全，但要新增一整套隔离的 Node 环境和构建校验，维护成本高，对现阶段来说太重

六、实施顺序

原则是先做低风险、高收益，并且每一步都能单独验收。新工作台挂在 /studio，和旧页面并存。

  1. 低风险设计系统和工作台外壳。深色专业配色、字体与间距令牌、三工作区的骨架、可折叠面板布局。只读展示项目和素材，不改任何接口。验收方式：看截图，并确认在 1366 和 1920 两种宽度下不出现横向滚动。
  2. 中风险剪辑区第一版：方案胶片条，加即时预览。输入需求 → 方案以缩略图条展示 → 点“预览”立刻播放 → 选中后导出成片。只用现有接口。验收方式：端到端流程“录像 → 方案 → 预览 → MP4”，并请你第三次试看 J1。
  3. 中风险时间轴与检查器：裁剪、替换、速度、转场，修改后即时预览，然后保存版本；“一句话改镜头”接入创作助手。用现有的剪辑版本接口，带回执哈希。
  4. 高风险口播优先与语音提供方。新增可替换的语音接口；成片长度由旁白长度决定；素材不够时明确提示。旁白和配乐显示为时间轴上的轨道，配乐支持拖入、起点、淡出。付费语音先做试听方案，等你批准。
  5. 中风险素材区并入：把首页的分析、检索、片段篮迁到素材区，片段可以“加入创作”（新增 eventIds 参数）。
  6. 低风险发布区：封面、文案、平台预览包。之后删除旧页面和它们的模拟测试，改由端到端流程保护。

判断第 1、2 步完成后，你就能感受到最大的变化：能看方案的视频，界面也是专业工作台的样子。第 4 步是唯一涉及费用和音频核心逻辑的一步，所以排在体验骨架稳定之后。
