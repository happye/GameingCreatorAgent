# 1. 项目背景与创业目标

本项目不是单纯为了做一个技术 Demo，而是以“一人公司”模式为前提，最终目标是做成一个可以商业化出售的软件产品。

创始人背景包括：

- 6～7 年软件开发经验；
- 主要技术栈：C、C++、C#、Shell、Linux、Windows；
- 有前后端与第三方工具开发经验；
- 有多年游戏短视频创作经验；
- 对游戏行业、游戏热点、视频内容制作流程较熟悉；
- 有真实的视频平台运营和变现经验；
- 长期关注 AI、大模型、开源模型、生图、生视频、Agent、自动化工具；
- 希望最终形成一套可以由个人开发、维护、运营并商业化的一人公司产品。

因此，本项目的核心原则不是“追求最大而全”，而是：

**利用创始人同时懂软件、游戏、内容创作和 AI 工作流的交叉优势，做一个足够垂直、足够实用、能够真实节约创作时间的商业产品。**

---

# 2. 产品最终定位

产品暂定名称：

**Gaming Creator Agent**

中文可理解为：

**游戏内容创作 Agent / 游戏视频创作智能工作台**

一句话定位：

> 用户提供一句创作需求、活动规则和原始游戏素材，AI 自动理解游戏内容、寻找对应素材、设计视频结构、生成脚本、完成粗剪、字幕、配乐和多平台版本适配，最终输出接近可直接投稿的完整内容包。

产品不是简单的：

- AI 剪辑软件；
- 高光识别软件；
- 游戏录屏软件；
- PR/剪映替代品；
- 单纯 Prompt 生视频工具；
- 通用视频 Agent。

真正的产品定位是：

**“从创作意图到可发布游戏内容”的完整自动化工作流。**

---

# 3. 核心产品价值

用户真正要解决的问题并不是：

> “帮我把视频剪短。”

而是：

> “我有很多游戏素材，我需要做一条满足某种内容目标的视频。”

例如：

- 做一条游戏攻略；
- 做一个角色介绍；
- 做一个玩法展示；
- 做一个实况精剪；
- 做一个游戏解说；
- 做一条游戏高光；
- 做一条活动投稿视频；
- 做一条游戏买量广告；
- 做一个新版本宣传视频；
- 做一个 B 站横屏版本；
- 再改成抖音、快手、小红书版本。

因此，产品价值应该从：

**“剪视频”**

提升为：

**“理解创作任务，然后完成整个内容生产流程。”**

- 降低剪辑工作量；

- 游戏市场部门；
- 游戏买量团队；
- 游戏内容代运营团队。

核心需求：

- 批量处理大量游戏实机素材；
- 快速制作游戏宣发视频；

- 自动生成不同平台的视频版本；
- 批量生成广告测试素材；
- 品牌一致性；
- 活动和平台规则自检；
- 团队工作流；
- 降低剪辑人力成本。

# 6. 一句话输入只是入口

产品可以让用户只输入一句自然语言，但系统内部必须把这句话转换为结构化需求。

例如：

> 帮我做一个 60 秒视频，展示这个游戏里的建筑破坏系统，发抖音。

内部转成：

```json
{
  "contentType": "feature_showcase",
  "game": "Example Game",
  "platform": "douyin",
  "duration": 60,
  "primaryGoal": "展示建筑破坏系统",
  "audience": "FPS 玩家",
  "tone": "高能",
  "aspectRatio": "9:16",
  "subtitle": true,
  "bgm": true
}
```

因此：

**自然语言负责交互，结构化数据负责系统执行。**

# 7. 内容模式

产品长期可以支持多个内容模式。

## 7.1 攻略模式

结构通常是：

```text
问题
↓
结论
↓
步骤 1
↓
步骤 2
↓
步骤 3
↓
注意事项
↓
结果
```

重点能力：

- 游戏知识理解；
- 素材检索；
- 操作步骤对齐；
- 解说稿生成。

---

## 7.2 游戏解说模式

结构：

```text
主题
↓
背景
↓
事件
↓
观点 / 信息
↓
对应画面
↓
总结
```

重点：

- 长文本组织；
- 画面与旁白匹配；
- 节奏控制。

---

## 7.3 实况精剪模式

重点不是极端压缩，而是：

- 去掉等待；
- 去掉重复跑图；
- 去掉加载；
- 去掉无效操作；
- 保留事件连续性；
- 保留主播情绪；
- 保留关键对话。

---

## 7.4 高光模式

识别：

- 击杀；
- 连杀；
- Boss；
- 稀有掉落；
- 反杀；
- 搞笑事件；
- 极端操作；
- 玩家强烈情绪。

该模式技术成熟度相对较高。

---

## 7.5 玩法展示模式

例如：

> 重点展示载具改装系统。

系统需要找：

- 进入改装页面；
- 零件选择；
- 外观变化；
- 参数变化；
- 实际驾驶；
- 改装前后对比。

这是本产品非常重要的差异化方向。

---

## 7.6 活动投稿模式

输入：

- 活动页面；
- 活动规则；
- 用户创作目标。

系统首先解析：

```text
指定游戏
指定话题
指定分区
时长要求
画幅要求
内容要求
原创要求
必须出现的游戏内容
禁止内容
投稿截止时间
```

然后创作。

最终自动进行：

**Preflight Validation / 投稿前检查。**

---

## 7.7 游戏广告 / 买量模式

输入：

> 做一个 20 秒广告，重点体现建筑可以完全破坏。

系统生成：

多个：

- Hook；
- 视频结构；
- CTA；
- BGM；
- 字幕；
- 节奏版本。

该模式价值不在生成一个“完美广告”，而是：

**快速生成大量合理测试版本。**

---

# 8. 第一阶段绝对不要同时做全部模式

产品最终可以支持多个模式，但 MVP 必须严格克制。

推荐开发顺序：

### 第一阶段

优先选择：

**玩法展示 + 活动投稿 / 攻略**

原因：

- 创始人自己能判断结果好坏；
- 可以直接使用自己的账号测试；
- 和纯高光剪辑竞争差异更明显；
- 能验证“AI 是否真正理解创作意图”。

---

# 9. 核心技术假设

整个项目最重要的技术假设不是：

> AI 能不能剪视频？

这一点已经基本不存在重大技术障碍。

真正需要验证的是：

> **现有多模态模型能否以足够低的成本，把数小时游戏录像转换成准确的语义时间线，并根据用户的创作意图找到真正有用的镜头。**

这是项目最核心的技术问题。

如果这一层成立：

后面的：

- 剪辑；
- 字幕；
- 音乐；
- 转场；
- 多平台导出；

基本属于常规软件工程。

# 15. 本地优先架构

游戏视频可能：

- 20GB；
- 50GB；
- 100GB；
- 数百 GB。

因此不要默认上传完整视频。

本地负责：

- FFmpeg；
- 转码；
- 抽帧；
- 音频提取；
- ASR；
- OCR；
- scene detection；
- Proxy；
- Cache；
- 最终渲染。

云端只处理：

- 必要关键帧；
- 小视频片段；
- 文本；
- 高级推理。

# 18. 视频理解

不要把一小时视频逐帧送给最贵模型。

采用：

```text
本地预处理
↓
稀疏抽帧
↓
便宜模型粗分析
↓
候选片段
↓
强模型精分析
```

最终每个片段形成：

```json
{
  "start": 530.2,
  "end": 541.8,
  "summary": "玩家使用爆炸物摧毁外墙后进入建筑并击杀敌人",
  "events": [
    "explosion",
    "wall_destruction",
    "enemy_kill"
  ],
  "features": [
    "destructible_environment",
    "breaching"
  ],
  "visualIntensity": 0.91,
  "clarity": 0.84
}
```

# 28. 为什么不直接控制 Premiere / AE

不建议后台自动操作 PR / AE。

原因：

- 自动化脆弱；
- GUI 操作难以稳定；
- 依赖授权；
- 版本差异；
- 难以部署；
- 难以批量。

Adobe 软件应该是：

**高级人工精修工具。**

不是自动化执行引擎。

---


# 69. 对开发 Agent 的总约束

任何后续负责开发的 Agent 都应遵守：

1. 不做通用视频编辑器。
2. 不做纯高光工具。
3. 游戏内容理解是核心。
4. Semantic Timeline 是核心基础设施。
5. 创作意图检索优先于复杂 UI。
6. AI 只生成结构化决策。
7. FFmpeg 负责视频执行。
8. 大视频默认本地处理。
9. 云端只处理必要 AI 推理。
10. 产品最终是 Windows Desktop EXE。
11. Agent-first，Timeline fallback。
12. 多平台适配必须独立成层。
13. 平台规则不得硬编码。
14. 活动规则必须支持结构化解析。
15. 商业化从第一天纳入架构，但 MVP 不做完整商业系统。
16. 模型必须可替换。
17. Prompt 必须版本化。
18. 模型成本必须可观测。
19. 用户修改行为必须被记录。
20. 每一阶段必须有明确 Go / No-Go 验证。

---

# 70. 交给其他 AI Agent 后首先要做的事情

不要让开发 Agent 第一件事直接生成整个项目。

第一步应要求它：

> 阅读本方案，从技术可行性、系统架构、模型能力、视频处理、商业化和工程风险六个角度，对方案进行一次完整的反向审查。

重点找：

- 哪些假设过于乐观；
- 哪些模块不需要；
- 哪些技术风险最大；
- 哪些 API / 模型能力可能不足；
- 哪些部分一人公司难以维护；
- 哪些地方成本可能失控；
- 哪些功能应该延后；
- V0.1 的真正最小闭环是什么。

完成审查以后，再进入正式技术架构设计。

# 71. 推荐给开发 Agent 的第一条任务

任务：

> 设计并实现 Gaming Creator Agent 的 Phase 0 技术验证版。不要开发正式 UI，不要开发商业系统。输入一段本地游戏视频，通过本地预处理、ASR 和视觉模型建立 Video Semantic Timeline，并实现自然语言搜索。输出候选视频片段及时间码。重点验证语义检索准确率、处理成本和速度。所有模型通过 Provider Interface 抽象，结果保存 SQLite，并记录模型、Token、成本、PromptVersion 和 Processing Time。

验收：

> 用户搜索一个明确的游戏机制时，Top 10 推荐素材中至少 70% 被人工判定为“可用”或“高度相关”。

只有通过这一关，项目才进入下一阶段。

# 72. 当前项目结论

基于目前全部讨论，项目暂时确定为：

**Gaming Creator Agent**

目标：

**面向游戏创作者、UP 主、主播、游戏工作室和游戏公司的 AI 游戏内容生产工作台。**

核心路径：

```text
一句创作需求
+
活动 / 平台规则
+
游戏素材
+
游戏知识
↓
AI 理解
↓
素材检索
↓
脚本规划
↓
自动剪辑
↓
人工修正
↓
多平台适配
↓
发布包
```

第一阶段不追求完全自动化。

合理目标：

**AI 完成 70%～85% 的重复性工作，人负责最后 15%～30% 的创意判断和精调。**

长期目标不是替代剪辑师，而是：

**让一个创作者或运营人员拥有过去数倍到数十倍的游戏内容生产能力。**
